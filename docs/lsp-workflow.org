#+title: Language Server Workflow

* Scope

这份文档描述当前语言服务器栈的运行方式、维护入口和扩展约定。

覆盖内容：

- 单一 =lsp-mode= 客户端与自动启动模型
- =Language Server Hub= 和 =Language Server Doctor=
- 常用运维命令和 session 级调参入口
- 如何注册新的 target-aware client
- 如何把这种 Hub/Doctor 模式继续扩到别的模块

相关入口文件：

- =lisp/init-lsp.el=：路由核心、Remote adapter 绑定、URI/workspace 身份、
  flymake/company/lsp-mode 装配，以及可见区域渲染边界
- =lisp/init-lsp-ops.el=：backend 无关的通用命令（restart/shutdown/log/session）
- =lisp/init-lsp-tools.el=：Hub、Doctor、dispatch、session 调参
- =lisp/init-lsp-runtime.el=：runtime provider 层，见下方 *Runtime Contexts*
- =lisp/init-lsp-toolchain.el=：project 级 toolchain profile（buffer-local
  环境变量/PATH 应用与复原）
- =lisp/lang/=：逐语言路由声明与 server 特有配置

* Design

当前只有一个受支持的客户端：=lsp-mode=。Eglot 作为 Emacs 内置库不能卸载，但
命令会从 =M-x= 隐藏，防止误启动第二套不受 Remote workspace 管理的客户端。

所有 file-backed =prog-mode= buffer 都会延迟尝试启动；只有同时满足以下条件才
真正连接：

- 当前 mode 有可用 client；
- client 所需 feature 可加载；
- language server executable 在当前 workspace target 的环境中存在。

自动启动找不到 server 时保持安静；手动执行 =my/language-server-ensure= 才显示
缺失提示。自定义 client 用 =my/register-language-server=，=lsp-java= 这类由包
自身注册的 client 用 =my/register-language-server-feature= 声明给 Hub/Doctor。

进程启动统一绑定到 Remote 框架的 =language-server= adapter。默认 placement 是
target：本地 buffer 使用 =local= target，远程 buffer 使用自己的 target/workspace
PATH、direnv 和工具链，不会把客户端机器上的 server 路径泄漏给远端。

普通 =find-file= 打开的 =/ssh:= / =/rpc:= buffer 不要求用户改成 =/fs:= 才能启用
LSP。client 匹配时会临时反映物理 TRAMP 身份，真正解析 executable、cwd、environment
和启动 stdio 时则进入 owning =/fs:= workspace；这沿用了旧 Eglot 适配里“contact
只负责协议、Remote workspace 负责 placement”的边界，但现在只保留一套 lsp-mode
client，不注册 =*-tramp= 副本。

目标端没有完整 analyzer 时，可信 target 可以按版本自动 provision：Python 优先使用
目标 PATH 内的 Pyright/BasedPyright，否则部署客户端已有的 relocatable Pyright bundle，
最后才回退到 pylsp/Jedi；Java 同样把完整 JDTLS bundle 缓存到目标端。大 bundle 通过
=remote-copy-file-to-target= 交给 backend 的批量传输（SSH 为 SCP），不会让普通 TRAMP
=copy-file= 阻塞编辑链路。打包、trusted-target 门禁、暂存解压、ready probe、不完整缓存
修复、原子发布与清理统一由 =remote-service-provision-directory= 完成；语言文件只保留
Pyright launcher/JDTLS 执行位等服务器特有准备。server 仍在 target 执行，不会退回
客户端运行。

CodeLens 默认开启，=SPC c L= 切换。CodeLens、inlay hints、文档颜色、文档链接和
semantic-token 预取统一限制在当前可见窗口加
=my/language-server-visible-render-margin= 行缓冲内；服务器响应、诊断状态与协议缓存
仍按整个 workspace 保存。Flymake 的行尾短诊断由 redisplay 覆盖可见诊断行，不需要
buffer-global sideline overlays。统一 idle 为 350ms。

文件 watcher 不属于可见区域渲染，不能为了远程性能直接关闭。动态 registration 会把
物理 TRAMP root 规范到 =/fs:=，由同一 Remote workspace 持有稳定 descriptor；Linux
target 优先运行路由后的 =inotifywait= 并直接重写事件路径，其他 backend 回退到其
公开 file-notify 实现。watcher 的停止、恢复、去重和 workspace 清理由 Remote 统一
管理。

所有 breadcrumb renderer 都使用通用 tab-line 左侧展示型 underlay，不占用
header-line。文件刚进入 =prog-mode= 时，breadcrumb.el 直接出现在这个位置；LSP
ready 后只把 provider 原位替换成 lsp-headerline，不发生纵向跳动。中央 buffer tabs
始终按整条 tab-line 的宽度布局，不再为 breadcrumb 左右对称留空；两者相交时 tab
覆盖 breadcrumb。上游 breadcrumb 的跳转 keymap、link 与 tab 行为全部移除，只重新
挂一个受控的 mouse-1 动作：打开 Treemacs、定位光标所在的 Imenu node、把焦点移到该
node 并 pulse；mouse-2/3、滚轮仍只属于真正的 buffer tab。path、project 与 symbol
face 使用 =aaron-ui= 的高对比 semantic tokens，并在换主题/新 frame 后重应用。
header-line 继续留给 Noema 这类 buffer-local 应用控件。

* Runtime Contexts

=init-lsp-runtime.el= 在普通 project/toolchain 之上提供可复用的 runtime provider
层。它用于“源码属于项目 A，但真实解释器由另一个运行时决定”的 buffer；Noema
Jupyter cell 是第一个 consumer，后续 REPL/run/debug 可以复用同一份 runtime
对象，但目前没有迁移这些子系统。

运行时契约包含稳定 ID、owning Remote context、真实 workspace root、tooling
environment、runtime environment、语言 toolchain profile、workspace configuration
和 idle timeout。lsp-mode upstream 只按 =PROJECT-ROOT + CLIENT= 查找 workspace；
本仓库在 workspace 的 client-side metadata 上补充稳定 runtime ID，并把查找键扩展为
=PROJECT-ROOT + CLIENT + RUNTIME-ID=。普通 buffer 只能匹配没有 runtime tag 的
workspace。因此同一项目的两个 kernel 不会错误共用 server，相同 runtime 则会复用
保温中的 server，也不会让普通 Python buffer 误接到 kernel 专用 server。

runtime ID 只参与 Emacs 侧 workspace 选择和 Remote resource handle。协议 root、URI、
进程 placement、environment 与 watch 始终使用真实逻辑根（包括
=/fs:TARGET:/path=）；同一逻辑根仍只有一个 Remote workspace owner。多个 kernel 的
resource key 在这个 owner 下用 runtime ID 区分，不能通过伪造 root 或绕过 Remote
来换取 server 隔离。

工具与解释器是两层：pyright/pylsp 等 analyzer 仍从 target/workspace tooling
environment 解析，kernel 只提供 =pythonPath=、=sys.path=、env 和 import 分析设置。
这避免每个 kernel 环境都重复安装 language server，同时保留 VS Code/Jupyter
式的解释器跟随手感。最后一个 runtime buffer 离开后由 provider 的 timeout 单独
保温（Noema 默认 600 秒），timer 会在
server 被复用或已死亡时幂等取消。

provider 可同步或异步解析。无法可靠推导的 runtime 必须返回明确 fallback reason，
不能静默猜 PATH；Hub 和 Doctor 会显示 runtime state、provider、target 和原因。

* Remote-First Invariants

Remote 框架是 LSP 的核心执行层，不是只在远程 buffer 上启用的兼容补丁。本地
=local= target 与 SSH/WSL/container target 必须经过同一套注册、route、environment、
process、URI 和 resource-lifecycle 流程。

每次 LSP 设计或修改都必须满足：

1. 一个 server/workspace 只有一个 owning logical root。**协议/框架身份**
   （workspace root、URI、server placement、诊断 key）始终统一到
   =/fs:TARGET:/path=（对外为 =fs://=），物理 =/ssh:=、=/rpc:= 和 target-native
   path 只在 backend 或协议边界短暂存在。**buffer 身份**不受此约束：普通本地
   buffer 按 AGENT.md 的规定继续用原生路径（=find-file= 打开的
   =/Users/...= 不会被强改成 =/fs:local:...=）。两者的桥接由 Emacs 自身的
   buffer 别名机制承担——=find-buffer-visiting= 的 =get-file-buffer= 层已经是
   file-name-handler 派发的，=/fs:= 已注册它，所以 =/fs:local:/path= 与其原生
   拼写互相解析，不需要改写任何 buffer 的 =buffer-file-name=。
   lsp-mode 的 raw diagnostics lookup 有一处绕开了这层别名，因此本仓库在
   =lsp--fix-path-casing= 上用 =my/lsp-mode--fix-path-casing-a= 收口 key 域。
2. server cwd、executable、PATH/toolchain、workspace settings、watcher、helper
   service 与 network channel 都从同一个 root 的 target context 派生。
3. URI 回调必须查询 lsp-mode workspace 所拥有的 root；不能用回调
   发生时的当前 buffer / =default-directory= 猜 target。否则两个 target 上相同的
   =/home/me/project= 会串成同一项目。
4. server placement 默认是 =target=。只有必须访问 Emacs UI、本机 xwidget 或浏览器
   的 helper 才显式使用 =client=；它与 target peer 的 stdio/TCP 仍由 Remote
   backend bridge/channel 建立。
5. language consumer 不得用 =file-remote-p=、target 字符串、TRAMP method 或
   backend ID 选择另一套 server、PATH、参数和功能。真实平台差异应表达为 target
   capability/toolchain preference；lsp-mode 自身的兼容修饰集中留在
   共享 adapter 边界。
6. watcher、helper service、forward/channel 等长生命周期资源要登记给
   =remote-workspace=。没有断线故障注入与重建测试时，不能宣称 LSP 已自动恢复。
7. 新增接入至少同时测试 =local= 与一个真实 remote target 的 root、URI、cwd、
   executable 和 environment；需要网络/helper 的接入还要覆盖取消、清理与重连。

如果现有语言模块仍按 local/remote 分别选择 contact 或修改 PATH，应把它视为迁移
债务，不能作为新语言的模板。框架缺少表达能力时，先补通用 =remote-*= API 及
native/remote backend，再接语言业务。

* Current Command Surface

最常用入口：

- =SPC c L=: 切换当前 buffer 的 CodeLens（默认开启）
- =SPC c s=: 打开语言服务器 dispatch
- =M-x my/language-server-manager=: 打开 =*Language Server Hub*=
- =M-x my/language-server-doctor=: 打开 =*Language Server Doctor*=
- =SPC c o=: organize imports
- =SPC c R=: restart language server
- =SPC c a=: code actions
- =SPC c f=: format buffer
- =SPC c r=: rename

dispatch 里现在有四组内容：

- Views: hub / doctor / docs
- Lifecycle: ensure / restart / shutdown / log / session / config
- Edits: code actions / organize imports / format / rename
- Tuning: restart policy / keep-alive / log-io / inlay hints / output max / log max

* Language Server Hub

命令：

- =M-x my/language-server-manager=
- 或 =SPC c s= 然后按 =h=

它展示：

- 当前 buffer 的 major mode、项目根、当前活跃 backend、workspace config
- 当前 runtime context、provider、target 与显式 fallback reason
- 一组 session 级便捷调参入口
- 注册的 lsp-mode client/feature 路由表
- 当前 runtime knobs

Hub 里的重点不是“列个状态页面”，而是：

- 状态能看
- 命令能点
- 配置定义文件能直接跳回去

常用按键：

- =g=: refresh
- =e=: ensure 当前 buffer 的首选 backend
- =r=: restart
- =k=: shutdown
- =l=: 打开 backend log
- =s=: session / connections
- =c=: workspace config
- =o=: organize imports
- =a=: code actions
- =f=: format
- =R=: rename
- =p=: buffer problems
- =P=: project problems
- =d=: buffer diagnostics UI
- =m=: diagnostics menu
- =A=: cycle lsp-mode restart policy
- =S=: toggle workspace keep-alive
- =L=: toggle =lsp-log-io=
- =I=: toggle inlay hints
- =M=: 设置 =read-process-output-max=
- =E=: 设置 language-server log size
- =D=: doctor
- =O=: 打开本文档
- =RET=: 对路由/映射条目跳回定义文件

* Language Server Doctor

命令：

- =M-x my/language-server-doctor=
- 或 dispatch 里的 =D=

Doctor 主要做静态和半静态排查：

- 关键 library 是否能找到
- 本地注册的 server executable 是否存在
- 当前 buffer 的路由、active backend、workspace config、runtime context/fallback
- 注册的 lsp-mode 路由摘要
- 当前 runtime knobs

如果 LSP 状态怪异，先开 doctor，而不是先猜。

* Quick Settings

Hub 和 dispatch 里的调参入口目前都是“当前 Emacs session 生效”，不是永久写回配置。

适合场景：

- 临时打开 =lsp-log-io=
- 临时放大 =read-process-output-max=
- 临时关闭/开启 inlay hints
- 临时调大 language-server log size

如果某个值验证有效，再把它真正改回：

- =lisp/init-lsp.el=
- 或对应语言模块

* Maintenance Model

现在语言服务器相关逻辑分成五层：

1. =lisp/init-lsp.el=
   路由核心、统一 Remote/LSP adapter、URI/workspace identity、全局
   LSP/Flymake/company 配置。这里只允许出现 lsp-mode 的兼容边界，不在这里
   建第二套本地/远程产品策略。
2. =lisp/init-lsp-ops.el=
   backend-agnostic 操作命令，例如 restart / shutdown / organize imports。
3. =lisp/init-lsp-tools.el=
   Hub、Doctor、dispatch、runtime knobs、可视化维护入口。
4. =lisp/init-lsp-runtime.el=
   Runtime provider 层，供“源码属于项目 A，真实解释器由另一个运行时决定”的
   buffer 使用（目前的唯一 consumer 是 Noema Jupyter cell）。
5. =lisp/init-lsp-toolchain.el=
   Project 级 toolchain profile：语言中立的 discover/apply/restore 契约，
   供所有 lsp-mode client 共用，避免每个语言重复实现 buffer-local
   环境变量/PATH/workspace-configuration 的应用与复原。

语言专项继续放在 =lisp/lang/= 下。

* Add A New Route

自定义 stdio client 用：

#+begin_src elisp
(my/register-language-server
 '(some-mode another-mode)
 '("some-language-server" "--stdio")
 :server-id 'my-some-language-server
 :executables '("some-language-server")
 :placement 'target
 :label "Some language server")
#+end_src

如果 package 自己调用 =lsp-register-client=，只声明 feature 与维护 metadata：

#+begin_src elisp
(my/register-language-server-feature
 '(some-mode) 'lsp-some-language
 :executables '("some-language-server")
 :placement 'target
 :label "Some language server")
#+end_src

不要为 remote target 注册第二个 =*-tramp= client。=/fs:= handler 与
=remote-make-process= 已经负责路径、placement 和进程边界；一个 server id 服务本地
与远端。语言专项 setup 可以像 C/Python/Java 一样 buffer-local 设置
=lsp-enabled-clients=，避免 stock/add-on client 抢占唯一 owner。

当前优先保证的三条 route：

- C/C++：唯一 =my-clangd= client；
- Python：唯一 =my-python= client，按 target 环境依次选择
  =pyright-langserver=、=basedpyright-langserver=，必要时 provision Pyright，再回退到
  =pylsp=、=jedi-language-server=；
- Java：唯一 =jdtls= owner，每个 project 独立 =-data= 与 configuration，remote
  target 通过 toolchain provisioning 获得同一 JDTLS bundle。

新增 route 完成前检查：

- contact 中没有物理 =/ssh:= / =/rpc:= path，也没有 local/remote 两套 client；
- executable 通过 target workspace environment 查找；
- URI round-trip 绑定 server/workspace root，而不是当前 buffer；
- workspace configuration 能深合并 plist/alist/hash-table，并保留显式 nil/
  =:json-false=；
- 需要 watcher/service/channel 时已经登记 workspace owner 和清理策略；
- =make lsp-test= 通过；本机安装相应 server 时 =make lsp-live-smoke= 真正初始化成功。
- 真实 SSH target 还要执行
  =REMOTE_LSP_E2E_TARGET=TARGET make lsp-remote-live-smoke=；它从普通物理 TRAMP
  buffer 启动 C/Python/Java，硬性验证 Remote 进程归属、诊断、typed Imenu、completion、
  hover/definition/references/rename/format/codeAction capabilities，以及真实 watcher 事件。

* Pattern For Other Modules

如果后面要给 project / shell / org / diagnostics 也补这种“陈列展示 + 管理 + 调参”界面，建议照这个结构做：

1. 主模块保留核心行为，不把维护入口越堆越大。
2. 单独拆一个 =*-tools.el= 文件。
3. 提供：
   - dispatch
   - hub
   - doctor
   - 少量安全、可回滚的 session 级调参入口
4. 主模块暴露少量 metadata / hook，让 hub 能看到“配置是怎么声明出来的”。
5. 单独补一份 workflow 文档，不把维护细节塞进 README 主叙事。

当前语言服务器这一套已经把这种模式跑通了，可以继续复用。

* Troubleshooting

如果某个 buffer 的语言服务器不工作，优先按这个顺序查：

1. 打开 =Language Server Doctor=
2. 看当前 buffer 的 =route policy= 和 =active backend=
3. 看当前 mode 是否有已注册且可执行的 lsp-mode client
4. 看对应 feature / executable 是否缺失
5. 看当前 buffer 的 =my/language-server--workspace-configuration=
6. 需要时临时打开 =lsp-log-io= 或调大 language-server log size
7. 再去开 log / session / problems / diagnostics UI

别一上来就改代码或重装 package。
