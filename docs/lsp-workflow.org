#+title: Language Server Workflow

* Scope

这份文档描述当前语言服务器栈的运行方式、维护入口和扩展约定。

覆盖内容：

- =eglot= / =lsp-mode= 的路由模型
- =Language Server Hub= 和 =Language Server Doctor=
- 常用运维命令和 session 级调参入口
- 如何为新语言补路由、补 Eglot server 映射
- 如何把这种 Hub/Doctor 模式继续扩到别的模块

相关入口文件：

- =lisp/init-lsp.el=
- =lisp/init-lsp-ops.el=
- =lisp/init-lsp-tools.el=
- =lisp/lang/=

* Design

当前策略不是“全局只用一个 LSP 客户端”，而是：

- 默认编程缓冲区走 =eglot=
- 少数明确声明的 major mode 走 =lsp-mode=

也就是：

- 默认路由：=prog-mode= -> =eglot=
- 显式例外：通过 =my/register-lsp-mode-preference= 把某些 mode 切到 =lsp-mode=
- 本地自定义 Eglot server 映射：通过 =my/register-eglot-server-program= 注册

这样做的好处是：

- 日常 buffer 保持 Eglot / Flymake 这套更轻的主路径
- Java、Beancount 这类需要专用 lsp-mode client 的语言仍然可以显式 opt-in；
  Lean 明确走 Eglot
- Hub 能直接反查“这个 mode 的路由是在哪个文件里声明的”

Eglot 与 lsp-mode 的进程启动统一绑定到 Remote 框架的
=language-server= adapter。默认 placement 是 target：本地 buffer 使用
=local= target，远程 buffer 使用自己的 target/workspace PATH、direnv 和工具链，
不会把客户端机器上的 server 路径泄漏给远端。

* Runtime Contexts

=init-lsp-runtime.el= 在普通 project/toolchain 之上提供可复用的 runtime provider
层。它用于“源码属于项目 A，但真实解释器由另一个运行时决定”的 buffer；Noema
Jupyter cell 是第一个 consumer，后续 REPL/run/debug 可以复用同一份 runtime
对象，但目前没有迁移这些子系统。

运行时契约包含稳定 ID、owning Remote context、真实 workspace root、tooling
environment、runtime environment、语言 toolchain profile、workspace configuration
和 idle timeout。Eglot 只在自己的 project lookup 动态范围内看到
=(my/language-server-runtime-project ROOT ID)=；普通 =project-current=、Projectile
和文件导航仍看到真实项目。因此同一项目的两个 kernel 不会错误共用 server，
相同 runtime 则会复用保温中的 server。

工具与解释器是两层：pyright/pylsp 等 analyzer 仍从 target/workspace tooling
environment 解析，kernel 只提供 =pythonPath=、=sys.path=、env 和 import 分析设置。
这避免每个 kernel 环境都重复安装 language server，同时保留 VS Code/Jupyter
式的解释器跟随手感。runtime buffer 不改全局 =eglot-autoshutdown=；最后一个
buffer 离开后由 provider 的 timeout 单独保温（Noema 默认 600 秒），timer 会在
server 被复用或已死亡时幂等取消。

provider 可同步或异步解析。无法可靠推导的 runtime 必须返回明确 fallback reason，
不能静默猜 PATH；Hub 和 Doctor 会显示 runtime state、provider、target 和原因。

* Remote-First Invariants

Remote 框架是 LSP 的核心执行层，不是只在远程 buffer 上启用的兼容补丁。本地
=local= target 与 SSH/WSL/container target 必须经过同一套注册、route、environment、
process、URI 和 resource-lifecycle 流程。

每次 LSP 设计或修改都必须满足：

1. 一个 server/workspace 只有一个 owning logical root。文档身份始终是
   =/fs:TARGET:/path=（对外为 =fs://=），物理 =/ssh:=、=/rpc:= 和 target-native
   path 只在 backend 或协议边界短暂存在。
2. server cwd、executable、PATH/toolchain、workspace settings、watcher、helper
   service 与 network channel 都从同一个 root 的 target context 派生。
3. URI 回调必须查询 Eglot server 或 lsp-mode workspace 所拥有的 root；不能用回调
   发生时的当前 buffer / =default-directory= 猜 target。否则两个 target 上相同的
   =/home/me/project= 会串成同一项目。
4. server placement 默认是 =target=。只有必须访问 Emacs UI、本机 xwidget 或浏览器
   的 helper 才显式使用 =client=；它与 target peer 的 stdio/TCP 仍由 Remote
   backend bridge/channel 建立。
5. language consumer 不得用 =file-remote-p=、target 字符串、TRAMP method 或
   backend ID 选择另一套 server、PATH、参数和功能。真实平台差异应表达为 target
   capability/toolchain preference；Eglot/lsp-mode 自身的 TRAMP 兼容修饰集中留在
   共享 adapter 边界。
6. watcher、helper service、forward/channel 等长生命周期资源要登记给
   =remote-workspace=。没有断线故障注入与重建测试时，不能宣称 LSP 已自动恢复。
7. 新增接入至少同时测试 =local= 与一个真实 remote target 的 root、URI、cwd、
   executable 和 environment；需要网络/helper 的接入还要覆盖取消、清理与重连。

如果现有语言模块仍按 local/remote 分别选择 contact 或修改 PATH，应把它视为迁移
债务，不能作为新语言的模板。框架缺少表达能力时，先补通用 =remote-*= API 及
native/remote backend，再接语言业务。

* Current Command Surface

最常用入口：

- =SPC c L=: 打开语言服务器 dispatch
- =M-x my/language-server-manager=: 打开 =*Language Server Hub*=
- =M-x my/language-server-doctor=: 打开 =*Language Server Doctor*=
- =SPC c o=: organize imports
- =SPC c R=: restart language server
- =SPC c a=: code actions
- =SPC c f=: format buffer
- =SPC c r=: rename

dispatch 里现在有四组内容：

- Views: hub / doctor / docs
- Lifecycle: ensure / restart / shutdown / log / session / config
- Edits: code actions / organize imports / format / rename
- Tuning: autoreconnect / autoshutdown / log-io / inlay hints / output max / events buffer

* Language Server Hub

命令：

- =M-x my/language-server-manager=
- 或 =SPC c L= 然后按 =h=

它展示：

- 当前 buffer 的 major mode、项目根、当前活跃 backend、workspace config
- 当前 runtime context、provider、target 与显式 fallback reason
- 一组 session 级便捷调参入口
- 显式 =lsp-mode= 路由表
- 本地注册的 Eglot server 映射
- 当前 runtime knobs

Hub 里的重点不是“列个状态页面”，而是：

- 状态能看
- 命令能点
- 配置定义文件能直接跳回去

常用按键：

- =g=: refresh
- =e=: ensure 当前 buffer 的首选 backend
- =r=: restart
- =k=: shutdown
- =l=: 打开 backend log
- =s=: session / connections
- =c=: workspace config
- =o=: organize imports
- =a=: code actions
- =f=: format
- =R=: rename
- =p=: buffer problems
- =P=: project problems
- =d=: buffer diagnostics UI
- =m=: diagnostics menu
- =A=: toggle =eglot-autoreconnect=
- =S=: toggle =eglot-autoshutdown=
- =L=: toggle =lsp-log-io=
- =I=: toggle inlay hints
- =M=: 设置 =read-process-output-max=
- =E=: 设置 =eglot-events-buffer-size=
- =D=: doctor
- =O=: 打开本文档
- =RET=: 对路由/映射条目跳回定义文件

* Language Server Doctor

命令：

- =M-x my/language-server-doctor=
- 或 dispatch 里的 =D=

Doctor 主要做静态和半静态排查：

- 关键 library 是否能找到
- 本地注册的 server executable 是否存在
- 当前 buffer 的路由、active backend、workspace config、runtime context/fallback
- 显式 =lsp-mode= 路由和自定义 Eglot 映射摘要
- 当前 runtime knobs

如果 LSP 状态怪异，先开 doctor，而不是先猜。

* Quick Settings

Hub 和 dispatch 里的调参入口目前都是“当前 Emacs session 生效”，不是永久写回配置。

适合场景：

- 临时打开 =lsp-log-io=
- 临时放大 =read-process-output-max=
- 临时关闭/开启 inlay hints
- 临时调大 =eglot-events-buffer-size= 看日志

如果某个值验证有效，再把它真正改回：

- =lisp/init-lsp.el=
- 或对应语言模块

* Maintenance Model

现在语言服务器相关逻辑分成三层：

1. =lisp/init-lsp.el=
   路由核心、统一 Remote/LSP adapter、URI/workspace identity、全局
   LSP/Flymake/company 配置。这里只允许出现 Eglot/lsp-mode 的兼容边界，不在这里
   建第二套本地/远程产品策略。
2. =lisp/init-lsp-ops.el=
   backend-agnostic 操作命令，例如 restart / shutdown / organize imports。
3. =lisp/init-lsp-tools.el=
   Hub、Doctor、dispatch、runtime knobs、可视化维护入口。

语言专项继续放在 =lisp/lang/= 下。

* Add A New Route

如果某个语言要显式走 =lsp-mode=，用：

#+begin_src elisp
(my/register-lsp-mode-preference 'some-mode 'some-lsp-feature)
#+end_src

说明：

- 第一个参数是 major mode
- 第二个参数是这个 mode 依赖的额外 feature；没有就省略
- Hub 会自动记录这个声明来自哪个文件

例如当前已有：

- =java-mode= / =java-ts-mode= -> =lsp-java=
- =lean-mode= -> Eglot（=lean4-infoview-bridge= + xwidget）

** Lean eglot route + xwidget infoview

Lean 4 使用自定义 =lean-mode=（=lisp/lang/lean/=），以 Eglot 作为 LSP 客户端。
不再依赖 =lean4-mode.el= 主文件（避免触发其 =lsp-mode= 注册），只加载其语法/缩进
子文件（=lean4-syntax=、=lean4-eri=、=lean4-input=）。

Eglot server program 通过 =my/register-eglot-server-program= 注册：
- Lake 项目（有 lakefile.lean/toml）：=lake serve=
- 单文件：=lean --server=

信息面板（infoview）走 xwidget-webkit + Node.js bridge：

- =C-c C-i= 确保 Eglot 已通过
  =lisp/lang/lean/lean4-infoview-bridge/lean-proxy.mjs= 启动；proxy 在 Emacs
  客户端运行，通过 stdio bridge 连接 workspace target 上的 =lake serve=，
  并把 React 版官方 =@leanprover/infoview= 提供给本地 xwidget side window。
- Emacs → infoview：=post-command-hook= 注入 =window.updateCursor=；文本变化通
  过 HTTP POST =/cursor= 同步到 bridge。
- Infoview → Emacs（反向通道）：infoview 动作 POST 到 bridge 的 =/editor/<cmd>=
  路由；bridge 再通过标准 LSP request/notification 交给 Eglot：
  - =show-document= 跳转到 goal 中点击的源码位置
  - =insert-text= 应用 "Try this" 建议
  - =apply-edit= 应用 code action 文本编辑
  - =restart-file= 触发 =lean-refresh-file-dependencies=
- 每个 Eglot proxy 实例拥有独立的端口文件；本地端口文件还会校验 owner PID，
  proxy 正常退出时只删除自己拥有的文件。并发重连或测试进程不会覆盖当前
  Infoview 的端口并留下白屏。

远程 Lean buffer 同样使用完整链路：

- =node=、=lean-proxy.mjs=、=dist/=、HTTP/SSE 和端口文件始终留在 Emacs
  客户端，不要求 target 安装 Node，也不部署 UI bundle；
- =lake serve= / =lean --server= 从 target/workspace 环境解析并在 target
  上运行；远端 direnv/Nix capsule 的 cwd、PATH 与变量被封装在 stdio bridge；
- proxy 使用本机 loopback 端口，xwidget 直接连接，无需端口转发；
- Eglot 文档 URI 进入 Emacs 后 canonicalize 为 =/fs:TARGET:/path=，不会保存
  =/rpc:= 或 =/ssh:= 物理链路身份。

=lean-infoview-remote-proxy-auto-deploy= 仅保留为旧配置兼容项，当前链路不再读取它。
关闭 Infoview proxy 时，远程 Lean 仍直接通过目标上的 =lake serve= 工作。

* Add A Custom Eglot Mapping

不要再直接散落：

#+begin_src elisp
(add-to-list 'eglot-server-programs ...)
#+end_src

现在统一用：

#+begin_src elisp
(my/register-eglot-server-program
 '(some-mode another-mode)
 '("some-language-server" "--stdio")
 :label "some-language-server"
 :executables '("some-language-server")
 :placement 'target
 :note "Short maintenance note.")
#+end_src

这样做的价值：

- Hub 能看到 modes -> server 的映射
- Doctor 能检查 executable
- 可以直接跳回配置定义文件
- =:placement= 默认就是 =target=；只有明确的本地 UI helper 才写 =client=

新增映射完成前再检查：

- contact 中没有物理 =/ssh:= / =/rpc:= path，也没有 local/remote 两套命令；
- executable 通过 target workspace environment 查找；
- URI round-trip 绑定 server/workspace root，而不是当前 buffer；
- 需要 watcher/service/channel 时已经登记 workspace owner 和清理策略；
- =local= 与 remote target 都经过同一注册，并有对应测试。

* Pattern For Other Modules

如果后面要给 project / shell / org / diagnostics 也补这种“陈列展示 + 管理 + 调参”界面，建议照这个结构做：

1. 主模块保留核心行为，不把维护入口越堆越大。
2. 单独拆一个 =*-tools.el= 文件。
3. 提供：
   - dispatch
   - hub
   - doctor
   - 少量安全、可回滚的 session 级调参入口
4. 主模块暴露少量 metadata / hook，让 hub 能看到“配置是怎么声明出来的”。
5. 单独补一份 workflow 文档，不把维护细节塞进 README 主叙事。

当前语言服务器这一套已经把这种模式跑通了，可以继续复用。

* Troubleshooting

如果某个 buffer 的语言服务器不工作，优先按这个顺序查：

1. 打开 =Language Server Doctor=
2. 看当前 buffer 的 =route policy= 和 =active backend=
3. 看是否命中了显式 =lsp-mode= 路由
4. 看对应 feature / executable 是否缺失
5. 看当前 buffer 是否有本地 =eglot-workspace-configuration=
6. 需要时临时打开 =lsp-log-io= 或调大 =eglot-events-buffer-size=
7. 再去开 log / session / problems / diagnostics UI

别一上来就改代码或重装 package。
