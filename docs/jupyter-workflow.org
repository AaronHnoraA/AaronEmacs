#+title: Jupyter Kernel Workflow

* Architecture

The local Jupyter and Noema workflows use ordinary kernelspecs. Remote
kernels are provided by the vendored =remote_ikernel= source under
=site-lisp/remote_ikernel=. No remote Jupyter Server is required: the launcher
starts the remote kernel over SSH or a scheduler and forwards its ZMQ ports.

* Noema 与 Remote workspace

Emacs 托管的 Noema 不再由客户端 Node 直接启动当前笔记的 kernel。打开
=/fs:TARGET:/path/note.md= 时，Remote broker 在同一 Target/workspace 中发现
kernelspec、以 workspace root 为 cwd 启动 kernel，并原子暴露 Jupyter 的五个
ZMQ channel。=.cell/= script 和 output mirror 保留在远端 note 同目录。

传输断开只释放 channel；重连后先探测目标 kernel。进程仍存活时重建 forwarding
并保留内存状态；进程已经死亡时下一次执行重建 kernel，并以 =stateLost= 报告
状态丢失。不会自动安装依赖或回退到客户端 kernel；使用 Remote Doctor 的 probe
检查目标 =python3=、=jupyter= 和 kernelspec。

=attach:= 与 =remote_ikernel= 继续用于显式 existing-kernel/Jupyter Board 工作流，
attached kernel 不归 Noema broker 杀死或自动重启。独立 desktop host mode 继续
使用 Node 本地 launcher。

Noema 通过 Edit 打开的 Python/Sage =.cell= buffer 会把当前 kernelspec 一并交给
Emacs。runtime provider 在 owning Target 上执行 kernelspec 的轻量 probe，读取
=sys.executable=、=sys.prefix= 和 =sys.path=，再让 Eglot 的 Python analyzer 自动
跟随 kernel；server binary 本身仍来自该 Target/workspace 的 tooling environment。
同一 runtime 复用 Eglot，不同 kernel runtime 使用独立 Eglot project identity，
最后一个 cell buffer 关闭后默认保温 10 分钟。

普通 Python/ipykernel kernelspec 可自动推导。项目自带 Python/Sage wrapper 在
=metadata.aaron.runtime.probe_argv= 声明 probe 入口。=attach:=、legacy
=remote_ikernel= 和没有 probe metadata 的不透明 launcher 不会被猜测；它们回退到
项目默认 toolchain，具体原因可在 Language Server Hub / Doctor 查看。笔记项目的
=:aaronnote-jupyter= 默认 kernel 仍可设置，但不要再用项目级 =:toolchain= 把 Python
固定到 Sage。

当前配置不启用 Jupyter 包可选的 =/jpy:= 和 =/jpys:= TRAMP 文件名处理器。该
处理器在 Emacs 31 的 TRAMP foreign-predicate 调用约定下与当前 Jupyter 包版本
不兼容；Jupyter 的普通执行、=remote_ikernel=、Jupyter Board 和 Noema broker
不依赖它。

The vendored baseline is upstream tag =0.4.6= at commit
=1c437edb9df017141a6357a90de751bb200bd9fb=. Local changes are documented in
=site-lisp/remote_ikernel/UPSTREAM.md=.

* Install and verify

Install the editable source into the configured Anaconda environment:

#+begin_src sh
make remote-ikernel-install
bin/install-remote-ikernel --check
#+end_src

The check must report version =0.4.6+aaron.1= and a module path below this
repository's =site-lisp/remote_ikernel= directory. Emacs startup only checks
the tool; it never mutates the Python environment automatically.

* Jupyter Board

Open the board with =M-x my/jupyter-board= or Hyper dispatch =j=. The board
shows:

- Jupyter, Python, remote_ikernel, and editable-source health;
- protected Core remote kernels;
- disposable Temporary remote kernels;
- all local and other kernelspecs visible to the configured Jupyter CLI.

Main keys:

| Key | Action |
|-----+--------|
| =a= | Add a remote kernel through the CLI transient |
| =e= | Edit/recreate the remote kernel at point |
| =m= | Move a remote kernel between Core and Temporary |
| =d= | Delete the current kernelspec |
| =C= | Delete all Temporary remote kernels |
| =RET= | Show the normalized fields and raw =kernel.json= |
| =o= | Open the kernelspec resource directory |
| =g= | Refresh |
| =?= | Open the full Jupyter dispatch |

Core deletion requires a full confirmation. Temporary kernels can be deleted
individually or in one batch. A legacy =rik_*= kernelspec without Aaron
metadata is treated as Core so an upgrade cannot accidentally remove it.

* Persistent group metadata

New remote kernels store their management data inside namespaced kernelspec
metadata:

#+begin_src json
{
  "metadata": {
    "aaron": {
      "remote_kernel": {
        "group": "temporary",
        "config": {}
      }
    }
  }
}
#+end_src

New kernels default to Temporary. Change a group from the board or CLI:

#+begin_src sh
remote_ikernel manage --set-group rik_ssh_example_python core
#+end_src

* Maintenance

Run the vendored Python tests before changing the launcher:

#+begin_src sh
/opt/homebrew/anaconda3/bin/python -m pytest -q site-lisp/remote_ikernel
#+end_src

The SSH implementation uses =StrictHostKeyChecking=accept-new=: first-use keys
are recorded, while changed keys fail instead of being silently accepted.
CLI output from Board operations is retained in =*Jupyter Board Log*=.
