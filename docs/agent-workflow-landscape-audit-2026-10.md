## 下一轮源码审计顺序

先核到的 Noema 事实：[`coordinator.go`](../site-lisp/noema/kernel/noema/research/coordinator.go) 已用 60 秒 claim lease 回收失联领取者，完成时检查 owner，并允许按请求 ID 查询 pending/claimed/done/failed；[`noema-agent-worker.el`](../site-lisp/noema/lisp/noema-agent-worker.el) 的 permission/input 回答经 host 权威下行及当前 worker epoch 校验；[`synthesis.go`](../site-lisp/noema/kernel/noema/research/synthesis.go) 的 Proposal review 使用版本检查。因此这里不是从零补一个通用审批系统。

1. **人机答复闭环**：用 agent-inbox 的回复领取与 Temporal 的等待恢复路径作为检查表，逐个追踪 Noema 的 ACP permission/input、coordinator request、Proposal review；记录请求 ID、答复版本、领取回执、重试与进程重启后的行为。重点查 host 已记录答复与 ACP callback 真正消费之间的回执；若已有完整机制，只补测试和文档。
2. **WorkNode 验收事实**：沿 Polaris `checks.py → engine.py` 对照 Noema 的结构检查、Run 结果、Artifact 和 Findings。Noema 的 [`completionConditionSatisfied`](../site-lisp/noema/kernel/noema/research/orchestration.go) 已对编排 Job 的冻结结果做键值精确比较，但它不是 WorkNode 的指标阈值或产物存在性检查。先定哪些条件是机器可验证的、哪些只可由人评审，再决定是否扩展源文档 schema。
3. **重复失败诊断**：用 OpenHands 的结构化循环检测对照 Noema ACP 事件与 Run transcript。先确认可观察到稳定的 tool identity、参数和错误结果，再考虑只读提醒；静默时间不能等同于循环。
4. **实验候选树**：用 AI-Scientist-v2 的失败节点与指标轨迹检验 Noema 现有 Run/Artifact 是否能对比多次尝试。若要新增树，应作为研究实验视图，不占用 WorkNode 的任务依赖语义。

这轮只完成候选筛选及上述源码切面核对，没有运行这些上游系统，也没有把它们的行为声明当成 Noema 需求。当前没有足够证据支持直接改动 Noema 的执行或审批策略。
