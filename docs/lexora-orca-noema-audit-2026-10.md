# Lexora / Orca ADE → Noema 功能代码审计（2026-10-02）

## 范围与版本

截图分别指向 [Lexora](https://github.com/useLexora/Lexora) 和 [Orca ADE](https://github.com/stablyai/orca)。以审计时的 Lexora [da2406a](https://github.com/useLexora/Lexora/tree/da2406ad908e18cb68ebe45500f44da11597f8a6)、Orca 官方仓库 [76c79f4](https://github.com/stablyai/orca/tree/76c79f473ad2eb71caa8f91e84119c0e373f751d) 及当前 Noema 工作树为准。Orca 搜索结果中的 zqm1221/OrcaADE README 自己指向 stablyai/orca，因此采用后者作为主线。审计按功能检查入口、状态权威、执行路径及失败边界；不是对 Lexora 约四千或 Orca 约三万一千个文件逐行证明。上游应用未在本机安装依赖或运行 GUI，结论均为源码静态结论。

## 已落实的 Noema 修复

1. [noema-agent-worker.el](../site-lisp/noema/lisp/noema-agent-worker.el) 现在保留 ACP rawInput 的字符串 command 和原始文件路径。当前安装的 agent-shell [测试](../elpa/agent-shell/tests/agent-shell-tests.el) 展示了 command 为字符串且没有 locations 的 tool call；旧 Action 只有 kind 和空 paths。
2. [permission_policy.go](../site-lisp/noema/kernel/noema/research/permission_policy.go) 对未知工具、缺少路径的读写和缺少结构化 argv 的执行改为人工决定；字符串命令仍参与硬拒绝和 Attention 显示，精确命令才能作为记忆规则。不带路径/命令的请求不能建立“始终允许”规则。
3. 同一策略文件用真实路径检查 symlink，包括尚未创建文件的现有父目录；指向项目外的链接不再被字面路径前缀自动放行，并在并发编辑比较中归并相同真实文件。
4. [runtime_test.go](../site-lisp/noema/kernel/noema/research/runtime_test.go) 与 [noema-api-tests.el](../site-lisp/noema/test/elisp/noema-api-tests.el) 覆盖字符串 push、缺信息、精确记忆规则和 symlink 逃逸。Go kernel 的 go test -tags fts5 ./... 与 Emacs make research-test 均通过。
5. 后续继续检查答复闭环时发现，Node 的 `delivered` 只表示 WebSocket 通知已排队，Emacs 原先却在调用 ACP 回调前清除待答复映射。[worker](../site-lisp/noema/lisp/noema-agent-worker.el) 现改为回调成功后清理；回调抛错会让 Run 明确失败并停止 ACP。成功续租会复查仍待答复的内核记录，按 Run、Session 和 epoch 恢复丢失的网关通知，且不会重复答复。活跃 Run 的畸形权限请求也不再退回 agent-shell 自有审批界面；迟到的 broker 回包不能复活已终止 Run。故障注入测试覆盖了权限、输入、自动审批、旧 epoch、回调同步结束和迟到回包。

验证：Emacs `make research-test`、`make jupyter-test`，Noema `make test`（2832 项通过）、`make build`、`make install`，Go `go test -tags fts5 ./...` 均通过。Node 命令使用仓库固定的 v26.5.0 / npm 11.17.0；系统默认 v26.7.0 不符合该仓库 `check-env`。`make install` 重建并重新链接了现有的 `~/.local/bin/noema-kernel` 目标。

### Agent 的角色与尝试身份

Orca [操作契约](https://github.com/stablyai/orca/blob/76c79f473ad2eb71caa8f91e84119c0e373f751d/skill-guides/orchestration.md#L25-L90) 明确区分 Coordinator、受监督 Worker、移交所有权的 Handoff owner。Worker 的心跳和最终报告同时携带 Task ID 与 Dispatch ID；一次 Task 重试生成新 Dispatch，旧 Worker 不再有结算权。[任务状态变更](https://github.com/stablyai/orca/blob/76c79f473ad2eb71caa8f91e84119c0e373f751d/src/main/runtime/orchestration/db/tasks/task-status-transition.ts#L14-L111) 也会核对活跃 Dispatch。Noema 已有 [Job claim、Invocation、epoch、上下文快照和 DisclosureView](../site-lisp/noema/kernel/noema/research/orchestration.go)；可借鉴的是统一的“当前尝试”投影和可见的交接状态，不能把 Agent transcript 或进程在线直接等同任务完成。

Orca 的 Task spec [要求](https://github.com/stablyai/orca/blob/76c79f473ad2eb71caa8f91e84119c0e373f751d/skill-guides/orchestration.md#L151-L164) 目标、变更、限制、编辑所有权和可观察验收。Noema [Task](../site-lisp/noema/kernel/noema/research/orchestration.go) 已有 objective 和 acceptanceCriteria，Job 另有 effects、budget、retry；为代码类 Job 增加明确的工作树/文件 owner 与验收证据，比再增加一个泛化 Agent 类型更有用。Orca 对远端 Worker 的 unverifiable 状态及“投递成功不等于已读”也适用于 Noema 的 ACP/Remote 状态显示。

### 继承什么，以及如何证明

- **会话继承**：Lexora [从指定 Run 前/后检查点启动](https://github.com/useLexora/Lexora/blob/da2406ad908e18cb68ebe45500f44da11597f8a6/apps/buddy/service/src/agent/sessions/tree/BuddyConversationTree.ts#L139-L187)，导航后验证实际 leaf；[恢复流程](https://github.com/useLexora/Lexora/blob/da2406ad908e18cb68ebe45500f44da11597f8a6/apps/buddy/service/src/agent/sessions/tree/BuddyTreeRecovery.ts#L12-L53) 记录缺失附件和重建图像数。Noema [D-031 路由](../site-lisp/noema/server/lib/research-session-routing.mjs) 已按 lineage 继续或分支，depends 不继承聊天；本地/远端不支持原生 fork 时重建上下文。可以增加统一的来源 Run/检查点和恢复降级展示，尤其让用户看清“原生 fork”和“重建 fork”的信息差异。
- **证据继承**：Orca 的 Worker 从自足 Task spec 和派发前言工作，不隐式承接 Coordinator 全部聊天。Noema [上下文解析](../site-lisp/noema/server/lib/research-runtime.mjs) 已把显式引用、直接父节点输出、lineage、Handoff、Skills 和审阅过的 Finding 冻结进带摘要的 RunSpec，并记录自动上下文的截断/遗漏。这一点比照搬聊天窗口更适合研究。
- **失败边界**：Noema 的 Work 输出允许 failed、cancelled、interrupted，[旧解析器](../site-lisp/noema/server/lib/research-runtime.mjs) 却只把其文本作为 result 上下文，丢失终态。本轮已修改为对非 completed 输出加来源 Run、终态和“部分/未验证”标记；不删除可能有用的部分结果。重建 fork 和显式引用取得的 Handoff 若来自未完成 Run，也会带状态提示，避免凭有 Handoff 就断言上游完成。
- **失效判断**：RunSpec 能证明“执行时看到了什么”，但 [readiness](../site-lisp/noema/server/lib/research-runtime.mjs) 当前主要看 WorkNode 的人工状态；上游输出更新后，没有看到按冻结父输出摘要自动标记下游待复核的机制。建议先增加只读的“本次 Run 所用父输出摘要 vs 当前父输出摘要”比较和提示，再决定是否自动传播 regressed；研究结论的撤回不宜只靠文件内容变化推断。

优先顺序：**P1** 在 Inspector 展示恢复降级，以及 WorkNode → Task/Job/Invocation/Run 的只读溯源；**P2** 上游证据更新后的待复核提示；**P2** 代码 Agent 的任务 owner、验收和远端不确定状态。以上后续项是设计建议，尚未实现。非 completed 输出与 Handoff 的来源标记已实现，Node 的 research-runtime 和 research-session-runtime 定向测试 59 项通过。

## 后续优先级与边界

- **P1，答复闭环剩余部分**：已处理 callback 抛错与通知丢失，但仍需为 permission/input 的 host resolved → ACP callback accepted → agent continued 建立持久分段回执。Emacs 重启时原 ACP 进程和回调对象不可恢复，应由 lease 到期/接管明确标记 Run interrupted；不能只依据数据库 resolved 或 Node 的 `delivered` 声称 Agent 已继续。
- **P1，可选代码 worktree**：仅对 Git code workspace 且用户明确启用的并行 Run，设计创建、锁、远端身份、未提交内容预检、产物归档与释放状态。研究文档仍由现有 Project/WorkNode 权威管理。
- **P2，变更覆盖率**：Run 的文件捕获若部分失败，要把 complete/partial/unknown 作为证据事实投影给 Inspector。不能凭空变更列表推断“Agent 没改文件”。
- **P2，定时检查**：若需要周期性文献/实验检查，先做生成待审任务的调度与错过记录，不自动重放有副作用的 Run。
- **当前限制**：Noema 的命令策略仍为 Action 文本启发式，真实文件系统会在授权后变化；本次修复缩小了可证明的绕过，但不构成 OS 沙箱。需要强隔离时应由执行后端提供并测试系统级目录/网络限制。上游仓库只作静态审计，没有运行 GUI 或完整上游测试。
