# 以文档为中心的 Emacs Agent 工作区

状态：设计草案，供用户审阅；不表示下述目标已经实现。现行行为仍以
[Agent 管理](../../design/agent-management.md)与
[批注](../../noema/design/comments.md)为准。源码学习及固定版本见
[sources.md](sources.md)，可执行任务与验证安排见 [实施计划](implementation.md)。

## 1. 目标与工作方式

用户要在自己的 Markdown 研究笔记、证明、设计和代码旁工作：选中一段，批注，交给
Agent；观察几十条任务，遇到问题在原处介入；Agent 把结果写回来，交给用户审阅。
任务进入 Todo → In Progress → Review → Done。交互使用我们的 Emacs / Noema
技术栈，学习其他项目的实现经验。

**文档是工作的地方，也是结果的归属。** 一条任务从文档中的问题开始，经过执行，
最后把可检查的结果带回文档。侧栏是这项工作的目录与仪表；会话是执行资源。

这条原则落实为以下约束：

1. 新建任务时保留发起文档、具体位置、请求和上下文；打开任务首先定位原文。
2. 证明、研究发现、设计决定写在其所属文档；任务中保存指向它们的链接及执行事实。
   不因一次派工自动创建 README、decisions、log 或另一份任务正文。
3. 批注的作用是提出问题、要求修改、补充反馈。批准对象是具体结果及修订，而非聊天结尾。
4. 任务总览、Agenda、图谱是同一工作事实的投影。切换视图不搬移任务、不复制正文。
5. 深入对话才打开 agent-shell。关闭侧栏、聊天或文档视图不结束后台执行。
6. 任务状态必须能沿链接回到来源与交付物。只有状态、没有可定位结果，不算完成。

### 一次科研任务

在 `proof.md` 的 Lemma 下选中一个假设，批注“这个假设是否必要？尝试构造反例”，
选择已有协作者。键盘仍在正文。侧栏出现该任务，排队时标出排队，真正执行后进入
In Progress。用户继续读另一篇文档。

Agent 把反例或推导写回 `proof.md` 的对应段落，必要时链接已有实验记录，提交
检查依据，任务进入 Review。用户打开该项，主编辑区回到 Lemma，查看结果、修订及
检查依据。接受后 Done；需要修改时在同一任务反馈，保留先前交付并发起下一次执行。

## 3. 从参考实现到我们的设计

详细源码位置与学习范围在 [sources.md](sources.md)。本方案采用以下判断：

- Nimbalyst：任务的工作状态、审阅阶段和会话关系分别建模；Review 后的批准需要人的操作。
  原生化为 Emacs 的任务投影与审阅动作，复用已有会话池和修订。
- SharpMD：在文档原处提出请求；任务能回到引文与文件。原生化为 region / point、
  marker、文件身份与 Noema 的源位置；实时事实读取已有 ACP / host 事件。
- TaskFlow：执行与交付是两件事，结果需要进入审阅。执行仍由现有 ACP 与原生队列负责。
- Lovelace、TaskNotes：记录可检查、局部写入基于最新文本、多视图共用写入边界。
  持久内容沿用 Markdown 与已有项目记录，原生界面不拥有第二份任务正文。

备选是继续在二态批注列表上加按钮，或另外做一套任务应用。前者无法表达交付与审阅，
后者会把文档变成任务附件。本草案选择把现有批注、执行回执和修订接成完整流程。

## 4. 对象与数据归属

| 对象 | 身份和归属 | 生命周期 |
| --- | --- | --- |
| 文档 | 现有文件 / Wiki 身份；框架边界规范为 `/fs:TARGET:/path` | 移动与重命名走已有文件生命周期 |
| 批注任务 | 文档身份 + 批注 id；请求与锚点沿用批注契约，生命周期在相邻任务记录 | 跨会话、跨 Emacs 重启保留 |
| 执行尝试 | task id + 唯一 attempt id，记录请求版本、作者、原生会话和 request id | 同一任务可有多次，晚到事件不能更改新尝试 |
| 交付 | 本次尝试的结果位置、验证说明、修订引用及文件版本 | 保留每次提交，供用户回看 |
| 会话 | 现有池中的协作者 | 可承接多项任务；任务不会随会话 buffer 消失 |
| 待处理原因 | 审批、提问、断开、冲突、任务说明已改变等事实 | 与任务的四阶段状态分别显示 |

会话仍只有一个主文件；处理其他文档任务不自动改绑。一个会话按原生队列串行处理
多项任务，多个会话可以并行；显示几十项任务不等于同时运行几十个进程。

### Markdown 与记录

正文保存研究内容及交付结果；批注保存请求与位置；相邻记录保存任务生命周期。
本轮不另造一套批注语法。源码里的 `@@comment` 与在途的选区锚点设计，均由所属
comments 契约维护；状态闭环只消费其“文档 + id + 请求 + 锚点 + 完成投影”接口。
代码等不能容纳正文批注的文件，继续使用现有的旁存任务适配器。

文件夹已有的 `.noema-comments.jsonl` 扩展为可重放的任务事实：attempt、指派、开始、
中断、提交、人工裁定、被替代的请求版本。生命周期值是 todo / doing / review / done；
每条事件含唯一操作 id、任务身份、前一任务 revision、执行 attempt、作者和时间。
它不复制已有 Markdown 批注的权威请求，也不收集聊天全文。

任务状态由该记录折叠；旧批注没有生命周期事件时按现有 open / done 语义投影。
已有结案标记继续可读。用户接受后同步既有批注的完成表示，重开时同步回 open；
外部手改完成表示时只记“源文件已变化”，不补造人工批准。未知事件保留并诊断，
重复事件按操作 id 幂等；相同 id 在同一文档重复时拒绝派工与状态写入。

沿用批注现有的只追加写入边界，host 与 Emacs 对同一日志追加事件。每条生命周期
事件注明期望的前一 revision；共享折叠规则只接纳匹配的状态转移，并按操作 id
去重。写入者重读确认该事件已接纳后才能报告成功；冲突事件保留作诊断并返回冲突，
不能用后写覆盖前写。JS 与 Elisp 用同一组 fixtures 核对折叠结果。

现有批注的 open / resolved 是同一折叠结果的兼容投影；接受任务的一个事件同时
产生 Done 与 resolved，无须依次修改两份状态。Markdown 的锚点保留原位文本。
无 host 时，Emacs 仍可读取日志、维护原生任务与会话；依赖 host 的文档编辑与
交付检查在能力就绪后执行。host 可用但失败时不绕过文档保存写盘。

复杂任务已有 `.agent/tasks/` 时，保留其原有身份与依赖规则；关联到文档和批注，
不复制为另一个可独立完成的任务。第一版不自动把每条批注提升为 DAG 节点，
也不改变项目图谱“另一位 Agent 复核”的现有语义。两种来源在侧栏明确标识。

## 5. 状态与交付

任务状态与执行状态分开，四阶段不会从会话的 busy / idle 猜测出来。

| 变化 | 触发条件 | 用户看到什么 |
| --- | --- | --- |
| 创建 → Todo | 批注保存确认 | 未分派或等待执行 |
| Todo → In Progress | 对应 attempt 的原生请求真正开始 | 执行者；需要时展开最近工具活动 |
| In Progress → Review | Agent 明确提交结果位置与检查说明，保存确认，attempt 与请求版本匹配 | 待审结果、修订与验证依据 |
| Review → Done | 人工接受本次交付 | 审阅人、交付版本；结果留在文档 |
| Review → Todo | 用户要求修改，保存反馈 | 同一任务待重做；下一次派工建立新 attempt |
| Done → Todo | 用户明确重开 | 保留先前交付，新问题版本待处理 |

“排队”“审批”“需要回答”“失败”“断开”“请求已修改”是附加原因，不新建另一套
任务状态列。失败或停止不进 Review，也不自动重试或结案；用户可以重试、改派或
撤回为 Todo。回合 `end_turn` 而未显式提交时标记“执行已结束，尚未交付”，供用户
检查或继续；不能据此宣称工作完成。

一个任务的同一请求版本只能有一个当前 attempt。重复点击交给 Agent 复用同一
派发操作；新尝试必须显式建立，已有输出不会被清空。原生队列被删除、修改或暂停，
任务必须显示对应事实，不得把已丢失的队列项继续标为执行中。

### 审阅与权限边界

Agent 的工具提供“提交审阅”，用户的原生操作提供“接受”“要求修改”“重开”。
Agent 的完成请求进入 Review，工具不允许以 Agent 身份代替用户批准。
旧的 Agent `comment {id}` 完成调用按新契约转为提交审阅；人工调用必须走独立的
交互动作，不能靠 JSON 中自报 `actor: human` 绕过。迁移时工具指南、全部入口及测试一起更新。

这约束的是协作 API 与界面操作。原生 Agent 仍能直接写文件；系统不伪称能阻止它
改状态源码。此类改动只显示为源文件状态变化，不产生“用户已批准”的审阅记录。

交付要列出结果所在文件及段落、已做的检查和未解决事项。API 可验证文件身份、
保存版本与修订引用，不能证明研究结论正确；用户审阅与科研核查仍是独立判断。
由任务关联的 pending 修订尚未处理时，完成动作先带到修订。拒绝某处修订不替人
推断整项任务结论；“要求修改”由用户明确作出。

## 6. Emacs 原生交互

### 文档与任务侧栏

复用 `H-t` 的固定侧窗及 Tasks / Pi / Graph 三页。默认仍在右侧，以免侵占已有
Treemacs 的位置；侧栏的位置由统一配置选择。主编辑区保持用户当前的源码 buffer
或 Noema 页面，公式、图和已有 Markdown 组件继续使用 CM6。

Tasks 页用 ETAF View / ref / Runtime 与公开 ETAF UI 组件构建，主题来自
`aaron-ui-etaf-provide-theme`；它挂在现有侧窗中，不额外打开管理浮窗。Pi 页继续是
真实 agent-shell buffer，Graph 页继续使用已有 SVG board。切页、收起与恢复遵守
现有窗口 owner，不重建 Pi 会话。

默认展示当前项目任务，支持本文件 / 文件夹 / 子树过滤；用户明确选定的范围保持
固定，切到另一篇文档不会把总览突然换掉。另有“跟随文档”选项。跨项目视图只读
显式进入或加入总览的项目，不遍历整个知识库，不把 git 根自动当成 Noema Project。

窄侧栏采用紧凑分组列表：需要我处理、Review、In Progress、Todo；Done 默认折叠。
每项显示请求短标题、来源文件与位置、执行者、任务状态及具体等待原因。支持按文字、
状态、执行者、优先级筛选；默认不为每项展开聊天或滚动日志。
计数以任务身份去重，排序稳定；事件刷新保留选中项、展开状态和滚动位置。

需要更大总览时在普通 Emacs buffer / frame 中展开同一投影，可按四阶段列显示；
窄屏继续用列表。第一轮先交付侧栏闭环，完整列布局不作为派工的前置条件。

### 发起、介入与定位

- 普通 buffer 继续用区域 / 光标处的批注命令；多行请求用普通可编辑草稿 buffer，
  短请求可用 minibuffer。取消保留未提交草稿，不产生任务或后台请求。
- Noema 页面继续选区批注；页面仅提供文档与批注交互，任务管理由原生侧栏承接。
- `RET` 打开任务的原文；展开详情显示原请求、执行次数、输出位置与待审修订。
  聊天是详情里的显式动作，沿用同一会话的窗口 owner。
- 对仍在执行的任务补充批注反馈，显示将进入本回合 steer 还是下一回合队列。
  遵守提供商能力及已有冻结回合规则；被拒的 steer 保留，不吞掉用户文字。
- 审批与 provider 提问打开其原生控件；回复送给确切请求，不把“回复任务批注”
  冒充 provider 表单回答，也不自动替人选择权限。
- 新动作进入 `tools/agent/actions` 的唯一动作表；面板与 Transient 复用该动作。
  延续 `H-t` / `H-T`，不再扩展一组全局快捷键。

锚点保存原文、前后文与基础版本。活着的源码 buffer 使用 marker 跟随编辑；
持久化定位用文件身份和文本上下文。重开后先核对原位置，再找唯一文本匹配；重复或
消失时仍可打开文档，但标明“需重新定位”，不跳到猜中的一处。行号只是提示。
Noema 的位置用其源文档与版本映射；UTF-16 和 Elisp 字符偏移在桥接边界换算。

### 文档内审阅

Noema 使用已有原位 ediff 卡片；普通文本使用原生 diff / Ediff、overlay 与关联
位置展示，复用同一份修订数据。接受 / 拒绝走现有受版本守护的写入，不新建浏览器
审阅台。Review 的入口回到结果段落，并展示这次尝试相关的多个文件。

原生工具的 ACP diff 仍按 C68 显示为“已直接应用”，并说明记录范围；G15 尚未
解决前不提供看似可靠的整任务撤销。用户批准的是看到的交付版本，后续文件改动会
提示需重新核对；研究结果的 Review 与通用文件差异不会被混为同一个证据。

## 7. 执行、保存与恢复

派工顺序：保存批注及身份 → 确认请求版本 → 建立并记录 attempt → 交给现有
会话的原生队列 → 绑定准确 request → 消费该 request 的生命周期事件。
任何一步失败保留请求与可恢复记录，不显示“已交出”，也不重复启动任务。

`tools/agent/requests` 扩展不采集聊天正文的生命周期观察模式，提供受 request 身份
约束的开始和终态事件。仍使用现有回执、队列和身份核对；文档任务不依赖
`agent-message-chunk` 或从最后一条回复提取结论。已有后台任务的结果采集保持原行为。

交付经协作 API 明确携带 task id、attempt id、请求版本、结果链接和检查说明。
文档编辑 / 提议接受这些关联字段；没有 task id 的普通修改继续有效，不被随意
归进“这个 Agent 当前看起来在做的任务”。晚到的旧 attempt 提交只进历史，不能
覆盖新任务状态。

打开的文档走既有保存 API，普通文件沿用 C74 buffer 规则。host 可用但保存失败时
保留操作并报告，不能绕过页面写盘；无 host 时保留待提交草稿。局部修改
必须唯一定位或版本守护；状态和交付保存也需要成功确认。重命名沿用既有服务更新
身份；只读文件、锚点失效或目标不可达均保留原请求。

崩溃恢复读取批注与持久任务记录。旧 request 的内存回执消失时显示“执行状态未知”，
不自动恢复为运行中，不凭会话 native id 重放提示。显式重试建立新 attempt。
记录中的一次派发意图有唯一操作 id；恢复遇到“已送达但确认未落盘”的不确定区间
先核查真实会话，不能把幂等文件写入等同于提供商执行 exactly-once。

远程文件继续通过 `remote-*` 能力路由，consumer 不按本地 / 远程分叉。当前 G14
的 host 工具转发仍是缺口；无此能力时禁用依赖该链路的派工并给出具体原因，不拿
客户端上的同名路径充当目标，也不把本地验收算作远程已支持。

## 8. Agenda、全局注意与性能

Agenda 的源仍是同一批注，合并对应任务生命周期。普通 todo 状态集暂不扩展为 review；批注投影额外保留
`commentState`，Review 以待处理项及 review 标签显示，状态写回由批注适配器解释。
原生和 Web Agenda 都要保留它，不能在 round trip 时把 review 静默写成 todo。
Done 的切换走同一人工裁定规则。执行回执、批注状态和任务图谱状态不相互猜测。

全局 Inbox 与 `/next` 可以跳到需审批、需回答或待审的文档任务；同一次等待只通知
一次。普通进展保持安静；需要人的通知直接打开对应文档或准确的原生审批控件。

状态源持久化与必要的请求生命周期订阅属于执行底座，侧栏关闭也要继续落盘。
视图订阅和重绘只在显示时运行；关闭后释放，重新打开从事实重建。ACP 事件与
`saved` / `comments-changed` 触发受影响项更新，不轮询 Agent，不按每个 token
刷新侧栏，也不按每次会话状态变化同步 rg 整个项目。

项目任务查询复用已授权的 scoped Agenda / 索引与批注解析，合并执行事实。
无 host 的文本模式在显式刷新时扫描所选范围，路由异步文件操作；隐藏时不维护
第二套后台索引。性能验收记录扫描次数、重绘次数和实际耗时，不能仅凭体感声称快。

## 10. 端到端验收

以下均为待执行的验收要求，不是已通过的测试记录：

1. 在带公式的 Lemma 选区创建请求；批注保存成功才交出，主编辑区焦点保持不变。
   保存失败不启动 Agent，草稿可恢复。
2. 两个会话处理 30 项任务；排队项不会被同会话另一任务的 busy 状态误标运行中。
   搜索、范围与状态筛选有效，事件刷新不移动选中项。
3. Agent 修改两个文件并提议一处修订；显式提交后进入 Review，点击回到原文，
   显示本次输出及检查依据。未处理修订可逐处审阅。
4. 用户要求修改；反馈留在同一任务，第二次执行保留首次交付，旧尝试的晚到事件
   不结案新尝试。用户接受后才记录人工批准与 Done。
5. 执行中出现审批、问题、失败、断开、取消或队列移除，各自显示真实原因；不会
   被 end_turn 或 idle 错当成完成，不自动重发可能已经产生改动的任务。
6. 重复引文、无 id / 重复 id、非 ASCII 文本、文件改名、并发改正文 / 请求 / 状态，
   均不误写另一处。已有未保存 buffer 的内容与保存权保留。
7. 重启 Emacs 后任务、结果和审阅记录仍可查看；丢失内存回执的任务显示待核查。
   API 重复提交不会重复建结果，不能确认的发送不重复执行。
8. 同一任务在侧栏、Agenda、文档、Inbox 中的状态一致；持久记录中的 Review 经各入口
   读写后仍为 Review。任务点击不默认打开聊天。
9. 侧栏隐藏后没有视图刷新订阅；活动任务仍能落盘。高频 ACP 活动合并更新，
   没有轮询和重复整项目扫描。GUI 与 TTY 都能完成核心操作。
10. 本地、远程及故障恢复按现有 Remote 契约分别核验；缺能力的入口如实报告，
    不将本地演示扩大为完整远程支持。
